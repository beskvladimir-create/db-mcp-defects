# Codebook (v1.0, fixed before labelling began, 2026-11-01)

Unit of analysis: one merged pull request (PR) in a study repository whose title or labels suggest a fix.
The annotator reads the PR title, PR body (and any issue it references, when that issue is in the
collected issue set), and the list of changed files. Each unit receives the fields below.

## F0 `include` (yes/no) and `exclude_reason`
Include iff the PR repairs a defect in the server's runtime behaviour that a client or calling agent
could experience (including server start-up and connection). Exclude, with a reason code:
- `docs`   documentation, README, examples, comments only
- `build`  CI, build, packaging metadata, release tooling, lint, formatting, dependency bumps
- `test`   test-only changes (flaky test, test fixture)
- `feature` new capability or enhancement presented as a fix but not repairing incorrect behaviour
- `refactor` internal restructuring without behaviour change
- `nonserver` defect in a non-server component (UI, SDK sample, website, CLI unrelated to serving tools)
- `unclear` the title/body/files do not allow a decision

## F1 `element` — which part of the agent-facing contract was wrong (one value, the primary one)
- `TOOL_DEF`  tool listing/definition: tool name, description, input/output JSON schema, annotations,
             which tools are registered or exposed (toolset filtering).
- `INPUT`     handling of tool arguments: parsing, type coercion, defaults, optional/nullable parameters,
             parameter binding/templating, identifier quoting or escaping of agent-supplied values.
- `INTROSPECT` schema/metadata discovery (list databases/tables/collections/indexes, describe columns,
             sample rows) returns wrong, incomplete or failing metadata.
- `EXEC`      execution of the operation itself: wrong query generated by the server, dialect/version
             handling, transactions, pagination/limits, wrong API call, wrong target object.
- `OUTPUT`    result serialisation/rendering: data-type conversion (dates, decimals, bytes, NULL,
             nested/JSON, big ints), truncation, formatting, encoding, structuredContent/outputSchema mismatch.
- `ERROR`     error reporting: error swallowed, wrong isError flag, uninformative/misleading message,
             crash instead of error result.
- `GUARD`     safety guardrails: read-only enforcement, permission/authorisation checks, injection,
             destructive-operation protection, data exposure/redaction.
- `SESSION`   connection/session/state lifecycle: pooling, reconnect, leaks, per-session state,
             concurrency, timeouts/cancellation of database work.
- `CONFIG`    configuration and credentials: config/env parsing, connection strings, authentication to
             the database or cloud API, start-up wiring.
- `PROTOCOL`  MCP protocol/transport: stdio/SSE/streamable HTTP, initialisation, notifications,
             JSON-RPC framing, protocol-version negotiation, client compatibility at protocol level.

Precedence when several apply: choose the element the fix changes to repair the reported behaviour;
if still tied, use order GUARD > TOOL_DEF > ERROR > OUTPUT > INTROSPECT > INPUT > EXEC > SESSION > CONFIG > PROTOCOL.

## F2 `symptom` — what the calling agent observes when the defect is triggered (one value)
- `SILENT`   the call reports success but the returned data or effect is wrong, partial, truncated or
             stale, with nothing in the response signalling the problem.
- `UNSAFE`   the call succeeds and does something it should not (writes in read-only mode, bypasses an
             authorisation boundary, exposes secrets/data).
- `MISLEAD`  the call fails, but the error is missing, opaque, generic, wrongly flagged (e.g. not
             isError), or points to the wrong cause.
- `REJECT`   a valid call fails with an error that reasonably describes what went wrong
             (the defect is that the call should have succeeded).
- `TOOLS`    the tool surface is broken: tools/list fails, a tool is missing/duplicated/unexpectedly
             exposed, or a schema is rejected by a client or model provider.
- `UNAVAIL`  the server does not start, cannot connect, crashes, disconnects, or the call hangs/times out,
             so the agent loses the tool or receives no answer.
- `OPERATOR` only an operator would notice (resource leak, log noise, performance) — no change in
             what the agent receives.
- `UNKNOWN`  the record does not allow a symptom to be inferred.
Rule: code the symptom described in the PR/issue; if not described, infer from the code change only when
the consequence is unambiguous, else `UNKNOWN`.

Derived (not hand-labelled): `detectable_by_agent` = symptom in {MISLEAD, REJECT, TOOLS, UNAVAIL};
`undetectable_by_agent` = symptom in {SILENT, UNSAFE}.

## F3 `client_specific` (yes/no)
yes iff the PR/issue states the defect manifests only with a particular MCP client, host application,
model provider or LLM (e.g. "Gemini rejects the schema", "Claude Desktop", "Cursor", "VS Code").

## F4 Agentic authorship (computed by script, not hand-labelled)
See scripts/agentic.py. A PR is agent-involved if its author login is a known coding-agent account or the
PR body / merged commit message contains a coding-agent signature (e.g. "Generated with Claude Code",
"Co-Authored-By: Claude", Copilot coding agent, Codex, Devin, Cursor, Jules, Gemini CLI markers).

## Decision rules added during labelling (v1.1; applied to all 376 units in pass 1)
These rules were made explicit while labelling and are recorded here so that others can reproduce the coding.
1. A fix delivered only by a dependency version change, pin or package-metadata edit is excluded as `build`,
   even when the underlying runtime failure was real (e.g. a server that cannot import after an upstream release).
2. Error-message rule: if the failing call returns the database's or API's own error that accurately describes
   the submitted request (e.g. `column "x" does not exist`), code `REJECT`; if the error is server-internal,
   driver-internal, generic (HTTP 500 / JSON-RPC internal error), self-contradicting or names the wrong cause, code `MISLEAD`.
3. Defects in tool descriptions or server instructions that steer the model wrongly are coded `TOOL_DEF`/`TOOLS`
   and flagged "description defect" in the note.
4. Logging, telemetry and analytics defects are coded `OPERATOR`.
5. Connection, authentication and start-up failures (including OAuth token refresh) are coded `UNAVAIL`; when the
   cause is concurrency (races, locks, pools) the element is `SESSION`, otherwise `CONFIG`.
6. Results that are correct but so large that they exhaust the client's context or payload limit, and results that
   include unwanted objects (system schemas), are coded `SILENT` and flagged "oversized" in the note.
7. A merged revert that removes a broken earlier fix is itself coded as a fix of the regression it removes.
8. PRs with an empty body whose title names neither a component nor a behaviour are excluded as `unclear`;
   when the title names the behaviour (e.g. "fix auth header in different ES versions") they are included and the
   symptom is `UNKNOWN` unless unambiguous.

## v1.2 (review round 1, 2026-11-01)
- New field `unsafe_kind` for units with symptom `UNSAFE`:
  - `policy`: the agent's own call did something a stated policy forbids (write in read-only mode, statement
    classifier bypass, write mode failing open, call executed under the wrong identity, over-privileged user created).
  - `vuln`: an attacker-facing weakness that does not change the answer to a benign agent call (SSRF, path
    traversal, DNS rebinding, session binding, token exposure, injection through tool inputs, tool output not fenced
    as untrusted data).
- Six labels were corrected after an independent review (listed in APPENDIX.md, section E). Rules 3 and 5 were
  applied to units where they had not been applied consistently.
- Rule 6 (oversized output coded `SILENT`) is reported with a sensitivity analysis without those units.
- Follow-up series (same defect fixed in several PRs) are listed in `data/defect_groups.csv` and used for a
  de-duplicated sensitivity analysis.
